# NR-400 ↔ 나비엔 클라우드 프로토콜

2026-10-30에 실제 기기(나비엔 스마트톡 NR-400, MXCHIP WiFi 모듈, MAC `04:78:63:a6:e1:4a`)에서 캡처한 패킷으로 해독한 내용입니다.
원본 캡처는 `captures/`에 있고, `tools/decode.py`로 다시 확인할 수 있습니다.

## 접속

| 항목 | 값 |
|---|---|
| 서버 | `krst2.naviensmartcontrol.com:7000` (DNS로 조회. AWS 서울 NLB, IP 여러 개) |
| 전송 | 평문 TCP. TLS·암호화·인증 토큰 없음 |
| 연결 | 보일러가 서버로 접속해 연결을 유지합니다. 보일러 쪽에 열린 포트는 없습니다. |
| 유지 | TCP keepalive 약 2.4초 간격, 앱 레벨 하트비트 약 30초~2분 간격 |

## 프레임 구조

```
f7 | kind | dir | 01 | MAC(6) | 42 04 | cmd | len(u16 LE) | payload(len) | CRC16(BE)
```

| 위치 | 의미 |
|---|---|
| `f7` | 시작 바이트 |
| `kind dir 01` | `03 01 01` = 보일러 → 서버 보고<br>`01 03 01` = 서버 응답<br>`02 03 01` = 서버 → 보일러 명령 |
| MAC | 보일러 WiFi 모듈 MAC |
| `42 04` | 고정값(기기 유형으로 추정) |
| `cmd` | 명령 코드 |
| `len` | payload 길이, little-endian 2바이트 |
| CRC16 | **CRC-16/BUYPASS** (poly `0x8005`, init `0`, 반사 없음, xorout `0`). 마지막 2바이트를 뺀 프레임 전체로 계산해 big-endian으로 붙입니다. |

## 명령

서버 응답의 cmd는 **보일러 cmd + `0x64`** 입니다.

| cmd | 방향 | 이름 | payload |
|---|---|---|---|
| `02` | B→S | 등록 | 85바이트 기기 정보. 앞 4바이트(`10 27 00 00`)를 응답에 그대로 넣음 |
| `66` | S→B | 등록 응답 | `00 08 01 00` + 등록 payload 앞 4바이트 |
| `01` | B→S | 하트비트 | 없음 |
| `65` | S→B | 하트비트 응답 = 시각 | `yy mm dd 요일 hh mm` (요일: 일=1 … 토=7, 한국 시간) |
| `cd` | S→B | 설정 요청 | 없음. 등록 후 첫 하트비트에서 보냄 |
| `05` | B→S | 설정/기능 정보 | 32바이트 |
| `69` | S→B | 설정 응답 | 등록 응답과 같음 |
| `cf` | S→B | 조회 | `00` = 상태, `0e` = 예약표 |
| `07` | B→S | 상태/예약표 보고 | 29바이트 상태, 또는 `0e`로 시작하는 281바이트 예약표 |
| `6b` | S→B | 보고 응답 | 보고 payload의 첫 바이트(`01` 또는 `0e`) |
| `ce` | S→B | 제어 | 아래 표 |

### 제어 (`ce`)

| payload | 동작 |
|---|---|
| `06 TT` | 온돌 모드, 설정온도 `TT/2` °C (예: `52` = 41°C) |
| `04` | 외출 |
| `01` | 끄기 |
| `02` | 켜기 (이전 모드로 복귀) |

명령을 받으면 보일러가 바뀐 상태를 `07`로 바로 보고합니다.
조절기에서 직접 조작해도 `07`이 올라옵니다.

### 상태 payload (`07`, 29바이트)

| 인덱스 | 의미 | 예 |
|---|---|---|
| 0 | 보고 종류 `01` | |
| 3 | 직전 난방 모드(추정) | `06`, `08` |
| 8 | **현재 모드** (`01` 꺼짐, `04` 외출, `06` 온돌) | |
| 10 | 미확인 온도(÷2), 난방수 온도로 추정 | `42` = 33°C |
| 11 | **실내 온도** (÷2) | `2e` = 23°C |
| 12 | **설정 온도** (÷2) | `50` = 40°C |
| 13 | 최대 설정 온도(÷2) | `5a` = 45°C |
| 나머지 | 미확인 | |

## 접속 순서 (실측)

```
B→S 02 등록          S→B 66 등록 응답
B→S 01 하트비트      S→B 65 시각, S→B cd 설정 요청
B→S 05 설정          S→B 69 응답, S→B cf 00 상태 요청
B→S 07 상태          S→B 6b 응답
… 이후 하트비트, 조회, 제어
```

## WiFi 등록 (프로비저닝)

`captures/PCAPdroid_30_Oct_14_35_40.pcap`(폰에서 PCAPdroid로 캡처)으로 해독했습니다. 구현은 `tools/provision.py`입니다.

- 설정 모드 진입: **보일러를 끈 상태에서 조절기의 [+] 버튼을 3초간** 누릅니다.
- 설정 모드에서는 보일러가 **암호 없는 AP `NR40-xxxx`**(xxxx는 기기마다 다름. 이 기기는 `NR40-8264`, BSSID는 모듈 MAC + 1)를 엽니다.
  - 보일러 주소: `192.168.43.1`
  - 접속한 기기 주소: `192.168.43.100`부터 할당
- 통신 방식: **평문 HTTP** `POST http://192.168.43.1/process_data.json`, `Content-Type: application/json`
  - 요청 하나를 처리하면 연결을 닫습니다. 요청마다 새로 연결하세요.
- 클라우드 토큰, 사용자 ID, 서버 주소는 **전혀 보내지 않습니다.** WiFi 정보만 넘깁니다.

요청 형식:

```json
{"command_id":"kdoneNNN","command_type":"<type>","request_value":"get|set"}
```

응답 형식:

```json
{"command_id":"incteNNN","command_type":"<type>","response_value":"ok","data":...}
```

| 순서 | command_id | command_type / request_value | 응답 data |
|---|---|---|---|
| 1 | `kdone001` | `validproduct` / `get` | `""` |
| 2 | `kdone003` | `productid` / `get` | `"047863a6e14a4204"` (MAC + `4204`) |
| 3 | `kdone004` | `scan` / `set` | `""` (검색 시작) |
| 4 | `kdone005` | `scan` / `get` (약 5초 뒤) | `{"scan list":[{"no","ssid","bssid","ch","rssi","security","pairwise","group","wps","mode"}, ...]}` |
| 5 | `kdone006` | `join` / `set` + `data` | `""` → 보일러가 해당 WiFi로 접속하고 AP가 사라짐 |

`join`의 `data`는 **키 하나짜리 객체들의 목록**이고, 순서는 아래와 같습니다. `bssid`부터 `group`까지는 scan 결과의 값을 그대로 넣습니다.

```json
[{"ssid":"…"},{"password":"…"},{"bssid":"B0:38:6C:…"},{"ch":"03"},{"security":"WPA2-PSK"},{"pairwise":"CCMP"},{"group":"CCMP"}]
```

> 설정용 AP는 암호화되지 않아서, 등록하는 동안 집 WiFi 비밀번호가 평문으로 공중에 오갑니다. 등록은 짧게 끝내세요.

## 미해독

- 등록(`02`)과 설정(`05`) payload의 세부 필드
- 예약표(281바이트)의 구조. `01 00 7f HH MM 0x TT` 형태가 반복되는 것으로 보입니다.
- 온수 모드, 반복/예약 모드 등 이번 캡처에 나오지 않은 제어 코드
